## Day 1 (Mon) — Git & GitHub Basics

### Theory

If you've used git before, this section is a refresh. If not, the [GitHub Skills](https://skills.github.com/) interactive courses are the best free option — do "Introduction to GitHub" first, then come back.

### The model

**git** = local version control. Every commit is a snapshot of your project. You move between snapshots, branch off them, and merge them.

**GitHub** = a cloud host for git repos with collaboration features bolted on (pull requests, code review, issues, Actions).

The unit of change is a **commit** — a small, atomic, named diff. The unit of *proposing* changes is a **pull request** (PR) — a branch you ask to merge into another branch, with discussion and review.

### The minimum git you need this week

```bash
git init                                # turn current folder into a git repo
git add .                               # stage all changes
git commit -m "Initial commit"          # create a snapshot
git branch -M main                      # name the default branch 'main'

# Push to GitHub (after creating an empty repo there)
git remote add origin git@github.com:YOUR_USERNAME/data-testing-practice.git
git push -u origin main

# Daily workflow
git checkout -b feature/add-customer-tests   # new branch off main
# ... edit files ...
git add tests/test_customers.py
git commit -m "Add 5 tests for customer data validity"
git push -u origin feature/add-customer-tests
# Open a PR on github.com from feature/add-customer-tests → main
```

### Why branches and PRs (not just commits to main)

In a real team, every change is reviewed before it merges. CI runs on the PR branch — **the goal of this week is making CI catch bad changes before merge, not after**. That requires the PR workflow. Even working solo, the discipline is worth practicing.

### Gotchas

1. **`.gitignore` doesn't unignore already-tracked files.** If you committed `dev.duckdb` once and then added it to `.gitignore`, it stays in git history. Use `git rm --cached dev.duckdb` to untrack it.
2. **HTTPS vs SSH for the remote URL.** HTTPS works everywhere but prompts for credentials. SSH (`git@github.com:...`) needs a key pair set up but is friction-free after. For frequent users, set up SSH.
3. **The default branch was historically `master`; modern repos use `main`.** Some old tutorials still assume `master`. `git branch -M main` renames it locally; GitHub lets you change it in repo settings.
4. **Force-pushing (`git push -f`)** rewrites history on the remote. Fine on your own feature branches; *never* on shared branches like `main`. You will lose colleagues' work.
5. **Commit messages matter.** "fix" tells nobody anything. The team-friendly format is a one-line summary, blank line, optional body. The summary should complete the sentence "If applied, this commit will…"

### Exercises

1. Create a new GitHub repo (private or public — your call) named `data-testing-practice`. Don't initialize with README — you'll push existing code.
2. In your project folder, run `git init`, add a `.gitignore` (per above), commit, and push to the new repo.
3. Browse to your repo on github.com. Confirm the file structure looks right and *no* `.duckdb`, `.venv`, or `__pycache__` files appear.
4. Create a feature branch `feature/add-readme`, add a `README.md` with a one-paragraph project description, push, and open a PR. Merge it.
5. **Bad-commit exercise:** make a commit with the message "fix" containing 200 lines of unrelated changes across 8 files. Then redo it as it should have been done — multiple smaller commits, each with a descriptive message. Compare the two histories with `git log`.
6. Add a basic `README.md` to your repo with: project goal, how to set up locally (the `pip install` from Week 2), how to run pytest, how to run dbt. This is what every team's README looks like.

## Day 2 (Tue) — GitHub Actions Intro

### Theory

**GitHub Actions** runs automated jobs against your repo when something happens. The "something" is called a **trigger** (push, PR opened, schedule, manual click, etc.). The "automated job" is a workflow defined in YAML, stored in `.github/workflows/`.

The hierarchy:

```
Workflow file                  (.github/workflows/test.yml)
└── Triggers                   (on: push, pull_request, schedule, workflow_dispatch)
    └── Jobs                   (test, lint, deploy — run in parallel by default)
        └── Steps              (run shell commands or use pre-built actions)
```

### A minimal workflow

Create `.github/workflows/hello.yml`:

```yaml
name: Hello CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:    # adds a "Run workflow" button in the GitHub UI

jobs:
  greet:
    runs-on: ubuntu-latest
    steps:
      - name: Say hi
        run: echo "Hello from $GITHUB_ACTOR on $GITHUB_REF"

      - name: Show files
        run: ls -la
```

Commit, push, and open the **Actions** tab in your repo on GitHub. You'll see the workflow run, the job inside it, and per-step output. Click into any failed step to see logs.

### Anatomy of a step

A step either runs **a shell command**:
```yaml
- name: Install something
  run: pip install ruff
```

Or uses a **pre-built action** (`uses:`):
```yaml
- name: Check out the repo
  uses: actions/checkout@v5
```

**`actions/checkout@v5`** is the action that clones your repo into the runner. Without it, the workflow doesn't see your code — the runner starts with an empty directory. Forgetting `checkout` is the #1 first-time bug.

### Triggers cheatsheet

| Trigger | When it runs |
|---|---|
| `push` | Any commit pushed (filter with `branches:`) |
| `pull_request` | PR opened, updated, or reopened (filter with `branches:`) |
| `schedule` | Cron expression — e.g. `cron: '0 6 * * *'` for 6 AM UTC daily |
| `workflow_dispatch` | Manual button in GitHub UI |
| `workflow_run` | After another workflow finishes |

For data testing, the typical setup is `pull_request` (run tests on every PR) plus `schedule` (run a daily sanity check on main).

### Runners

`runs-on: ubuntu-latest` — GitHub provides a fresh Ubuntu VM for each job. Other options: `macos-latest`, `windows-latest`. Linux is cheapest (free tier minutes go further) and what most data tooling assumes.

### Gotchas

1. **Forgetting `actions/checkout@v5`.** The runner starts empty. If your step says `pytest` but the test files aren't there, this is why.
2. **Pinning action versions.** `@v5` floats to the latest 5.x — usually safe. `@latest` is dangerous (breaking changes can ship overnight). `@v5.0.0` is fully pinned. For maximum security, pin to a SHA. For learning, `@v5` is fine.
3. **Each step runs in a fresh shell.** A `cd` in step 1 doesn't persist to step 2. Use `working-directory:` on the job or each step instead.
4. **Secrets are write-only.** Set them in repo Settings → Secrets and variables → Actions. Reference as `${{ secrets.MY_SECRET }}`. They're masked in logs (replaced with `***`) but never echo a secret to logs deliberately — log injection is a real risk.
5. **The free tier is generous but finite.** 2,000 free minutes/month for private repos; unlimited for public repos. Linux runners cost 1×, macOS costs 10×, Windows costs 2×. Stay on Linux unless you need OS-specific testing.

### Exercises

1. Create the `hello.yml` workflow above. Push to a feature branch, open a PR, watch it run.
2. Add a second job `info` that runs *in parallel* with `greet` and prints `python3 --version` and `git --version`. Confirm the Actions UI shows both jobs running side-by-side.
3. Make `info` *depend on* `greet` finishing first. (Hint: `needs: greet`.) Confirm it now waits.
4. Trigger the workflow manually via the "Run workflow" button. Did it run? Notice the trigger source in the run summary.
5. Add a step that *intentionally fails* (`run: exit 1`). Push. Confirm the PR shows a red ✕ and that the failed step's log explains why.
6. **Trap exercise:** remove the `actions/checkout@v5` step. Add a step `run: cat README.md`. Push. Why does it fail? What's the error message?

### External practice

- [GitHub Actions Quickstart (official)](https://docs.github.com/en/actions/quickstart) — concise, current
- [Awesome Actions](https://github.com/sdras/awesome-actions) — curated list of pre-built actions; skim the categories
- [actions/checkout README](https://github.com/actions/checkout) — see what `with:` parameters it accepts (fetch-depth, submodules, etc.)

## Day 3 (Wed) — pytest in CI

### Theory

Today you make every pytest test you wrote in Weeks 2–4 run automatically on every PR. The pattern is short.

### The full pytest workflow

Create a `requirements.txt` in your project root:
```
pandas>=2.0
pytest>=8.0
pandera>=0.20
scipy>=1.10
great_expectations>=1.0
```

Then `.github/workflows/pytest.yml`:

```yaml
name: pytest

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Check out
        uses: actions/checkout@v5

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: 'pip'              # auto-caches based on requirements.txt

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt

      - name: Run pytest
        run: pytest -v --tb=short
```

That's it. Push it, open a PR, watch your tests run. Every future PR will run them too.

### Speed: caching pip dependencies

The `cache: 'pip'` parameter on `setup-python@v5` automatically caches the pip download cache, keyed on your `requirements.txt`. First run is ~60 seconds; subsequent runs with the same `requirements.txt` are ~10 seconds.

If you use Poetry, `uv`, or pip-tools, the cache key changes — see [setup-python's docs](https://github.com/actions/setup-python#caching-packages-dependencies) for the right glob.

### Matrix: multiple Python versions

If you need to test against multiple Python versions, use `strategy.matrix`:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ['3.10', '3.11', '3.12', '3.13']
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pip install -r requirements.txt
      - run: pytest -v
```

This runs four parallel jobs — one per version — each gets its own runner. Great for libraries; usually overkill for an internal data project.

### Branch protection — require CI to pass before merge

CI that runs but doesn't gate merges is half a feature. Configure branch protection:

1. Repo → Settings → Branches → Add rule for `main`
2. Check "Require a pull request before merging"
3. Check "Require status checks to pass before merging"
4. Search for and select your `pytest` job

Now broken PRs literally cannot merge. This is the discipline that makes CI worth it.

### Gotchas

1. **Tests passing locally but failing in CI.** Common causes: hardcoded paths (`/Users/me/...`), local-only dependencies, timezone or locale differences, files that exist on your machine but aren't committed, environment variables set in your shell. Reproduce by running tests in a clean Docker container before debugging CI.
2. **Slow CI is unused CI.** If pytest takes 8 minutes, people stop waiting and merge anyway. Aim for under 2 minutes total. Use `pytest -n auto` (with `pytest-xdist`) for parallelism, scope expensive fixtures to `session`, skip slow tests on PR (`-m "not slow"`) and run them on schedule.
3. **`pytest --tb=long` (the default)** prints huge tracebacks. In CI logs that's noisy. `--tb=short` is much more readable.
4. **Tests that depend on the current date will fail intermittently.** A test asserting "this date is in the future" passes today, fails next year. Use frozen time (`freezegun` or `pytest`'s monkeypatching).
5. **Caching the wrong thing.** Caching `.venv` is faster than `pip` cache but invalidates harder. Caching `__pycache__` is pointless. Stick with `cache: 'pip'` until you measure a problem.

### Exercises

1. Add `requirements.txt` to your project. Push.
2. Add `.github/workflows/pytest.yml` from above. Open a PR. Confirm pytest runs in CI and matches your local output.
3. Deliberately break a test (change an assertion to fail). Push. Confirm the PR is blocked from merging — assuming you've set up branch protection.
4. Add `pytest-xdist` to `requirements.txt` and change the run step to `pytest -v -n auto`. Time the difference.
5. **Caching exercise:** push your workflow once, then push a no-op change. Compare the "Install dependencies" step's duration between the two runs. The second should be markedly faster.
6. **Failing-test artifact upload:** add an `actions/upload-artifact@v4` step that uploads `pytest_report.html` on failure (you'll need `pytest-html` and pass `--html=pytest_report.html`). Now PR failures include a downloadable HTML report.

- [pytest CLI options](https://docs.pytest.org/en/stable/reference/reference.html#command-line-flags) — knowing the flags pays off in CI tuning
- [setup-python advanced usage](https://github.com/actions/setup-python/blob/main/docs/advanced-usage.md) — caching, matrix, multiple Python installations

## Day 4 (Thu) — dbt in CI

### Theory

Running dbt in CI is conceptually identical to pytest — install, run a command, fail the workflow if anything errors. The wrinkle is that dbt needs a **warehouse**. Two patterns:

1. **dbt-duckdb in CI** — DuckDB runs entirely in-process. The warehouse is a file in the runner's filesystem. No external service, no secrets, no cost. Perfect for learning and small projects.
2. **A real warehouse via secrets** — Snowflake, BigQuery, Redshift, Databricks. The CI runner authenticates via secrets and runs against a CI-dedicated dataset. This is the production pattern.

We'll use #1 because it works without any external account.

### The dbt-duckdb workflow

Create `.github/workflows/dbt.yml`:

```yaml
name: dbt

on:
  pull_request:
    branches: [main]
    paths: ['ecom_dbt/**', '.github/workflows/dbt.yml']
  push:
    branches: [main]

jobs:
  dbt-build-and-test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ecom_dbt        # adjust to your dbt project folder

    steps:
      - uses: actions/checkout@v5

      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: 'pip'

      - name: Install dbt
        run: pip install dbt-core dbt-duckdb

      - name: Set up profiles.yml
        run: |
          mkdir -p ~/.dbt
          cat > ~/.dbt/profiles.yml <<EOF
          ecom_dbt:
            target: ci
            outputs:
              ci:
                type: duckdb
                path: ./dev.duckdb
                threads: 4
          EOF

      - name: Seed
        run: dbt seed --target ci

      - name: Build & test
        run: dbt build --target ci    # runs models AND tests in dependency order

      - name: Source freshness
        run: dbt source freshness --target ci
        continue-on-error: true       # warn-only for sources in CI
```

Note: `paths:` filters the trigger so the workflow only runs when files in the dbt project actually change. Saves CI minutes.

### Why `dbt build` instead of `dbt run` + `dbt test`

`dbt build` is the production-grade combination: it builds a model, immediately runs its tests, and only proceeds to downstream models if upstream tests pass. A bug at the silver layer halts gold-layer builds — exactly the behavior you want in CI.

### Real-warehouse CI (preview, won't do today)

If you target Snowflake instead of DuckDB:

```yaml
- name: Set up profiles.yml
  run: |
    mkdir -p ~/.dbt
    cat > ~/.dbt/profiles.yml <<EOF
    ecom_dbt:
      target: ci
      outputs:
        ci:
          type: snowflake
          account: "${{ secrets.SNOWFLAKE_ACCOUNT }}"
          user: "${{ secrets.SNOWFLAKE_USER }}"
          password: "${{ secrets.SNOWFLAKE_PASSWORD }}"
          role: "CI_ROLE"
          database: "CI_DB"
          warehouse: "CI_WH"
          schema: "ci_${{ github.run_id }}"
          threads: 4
    EOF
```

The `schema: ci_${{ github.run_id }}` trick gives each PR its own isolated schema. Drop it after the run with a teardown step. This is the "Slim CI" foundation.

### Slim CI (advanced — preview)

Real teams don't run all 500 models on every PR. They use **Slim CI**: only build models that changed (and their downstream dependents), comparing against a "production manifest" stored from the last successful main build.

```bash
dbt build -s state:modified+ --defer --state /path/to/prod-manifest
```

This is one of the strongest reasons to invest in dbt CI properly. We won't implement it today, but [the dbt docs page](https://docs.getdbt.com/docs/deploy/continuous-integration) covers it.

### Gotchas

1. **`profiles.yml` paths in CI.** dbt looks for `~/.dbt/profiles.yml` by default. Either create it inline (per the workflow above) or commit a CI-specific profile and pass `--profiles-dir`. Don't commit a profile with secrets.
2. **DuckDB in CI is ephemeral.** Each run starts with no database, so you need `dbt seed` before anything else. On a real warehouse, the schema persists between runs, but each PR should still start "fresh" via the schema-per-run pattern.
3. **`continue-on-error` vs `if: failure()`.** `continue-on-error: true` makes a step not fail the job. `if: failure()` runs a step only if a *previous* step failed (useful for cleanup or notifications). Don't confuse the two.
4. **Source freshness in CI is awkward** because the data is static (a seed CSV). The freshness check will always fail unless you `continue-on-error: true` or skip it in CI. Run real freshness checks against production on a schedule, not on PRs.
5. **dbt logs are verbose.** Use `dbt build --no-print` or `--log-level warn` to reduce CI log clutter. Default is fine while learning.

### Exercises

1. Add the `dbt.yml` workflow to your project. Adjust `working-directory:` to match your dbt project folder.
2. Push to a PR branch. Watch the workflow run — confirm `dbt seed`, `dbt build`, and `dbt source freshness` all complete.
3. **Break a test:** modify one of your `accepted_values` lists in `schema.yml` to be wrong (e.g. exclude `'completed'`). Push. Confirm the workflow fails at `dbt build` with the test failure visible in the log.
4. **Slim CI prep (optional):** add an `actions/upload-artifact@v4` step to upload `target/manifest.json` after a successful `main` build. This is the foundation Slim CI needs.
5. **Combine pytest + dbt:** in a *single* workflow file, define two jobs (`pytest` and `dbt`) that run in parallel. Confirm both show as required status checks in your branch protection settings.
6. **Trap exercise:** remove the `dbt seed` step. What error does `dbt build` produce? What does that tell you about the assumed state of the warehouse?

## Day 5 (Fri 🤖) — AI Workflow: Generate & Debug CI Pipelines

### What you're learning today

Two skills: (1) using AI to **debug a failing CI log**, and (2) using AI to **scaffold a multi-job workflow**. CI YAML is verbose, error messages are cryptic, and the work is high-leverage — small fixes that unblock the whole team. Perfect AI territory.

### Setup (~5 min)

- Have your `pytest.yml` and `dbt.yml` workflows from Days 3–4 ready
- Open Claude or Cursor

### Exercise 1 — Debug a failing log

Find a real failing CI run from Days 3–4 (you broke a test on purpose, or a real flaky run). Click into the failed step on github.com, click "View raw logs," and copy the relevant section. Paste into Claude:

> *"This GitHub Actions step failed. Diagnose the error and give me the fixed YAML. Here's the log:*
>
> *[paste raw log — keep it focused, 50–200 lines is plenty]"*

The AI will usually:
- Identify the actual error line correctly (good)
- Suggest a plausible fix (sometimes correct, sometimes not)
- Occasionally hallucinate an action that doesn't exist (always verify on GitHub Marketplace)

Apply the suggested fix manually. **Don't blindly trust the patch** — diff it against your existing YAML and make sure the change does what you'd write yourself.

### Exercise 2 — Generate a multi-job workflow from scratch

Prompt:

> *"Generate a complete `.github/workflows/ci.yml` for my project with these requirements:*
> *- Triggers: pull_request to main, push to main, and a daily schedule at 6 AM UTC*
> *- Three parallel jobs:*
> *  1. `lint` — runs `ruff check .` against Python files*
> *  2. `pytest` — installs from requirements.txt, runs pytest -v*
> *  3. `dbt` — installs dbt-core + dbt-duckdb, runs dbt seed && dbt build inside ./ecom_dbt/*
> *- Use actions/checkout@v5 and actions/setup-python@v5*
> *- Cache pip dependencies*
> *- Each job uses Python 3.12*
> *- Don't include any actions or services I don't need.*
>
> *Return only the YAML, no explanation."*

Save the output, push it, watch what happens. Common AI failures here:

- **Invented actions**: `runs-on: dbt-runner` (doesn't exist), `uses: dbt-labs/setup-dbt@v1` (real but you may not need it)
- **Outdated action versions**: `actions/checkout@v3` instead of `@v5`
- **Wrong syntax for matrix or schedule**: cron expressions are easy to get wrong; ask for `'0 6 * * *'` and verify with [crontab.guru](https://crontab.guru/)
- **Mixing `${{ }}` expression contexts**: `${{ secrets.X }}` works in `with:` and `run:`, but not everywhere

### Exercise 3 — Iterate on an existing workflow

Open your `pytest.yml` in Cursor. Use inline edit (`Ctrl+K`):

> *"Add a job that runs `coverage` and uploads a coverage report as an artifact. Don't change the existing pytest job. Use modern pytest-cov + actions/upload-artifact@v4."*

Review the diff. Did the AI:
- Create a new job correctly (parallel, not nested under the existing one)?
- Use real action versions?
- Wire up the artifact path correctly?

Fix what's wrong manually. **The reviewing-AI-output muscle is now in its 7th week** — you should be quick at this.

### Update your `.cursorrules`

Add a CI section:

```
GitHub Actions conventions:
- Pin action versions to a major (e.g. @v5), never @latest or @main.
- Use `actions/checkout@v5` and `actions/setup-python@v5` (verify current via Marketplace if pinning higher).
- Always include `cache: 'pip'` on setup-python when there's a requirements.txt.
- Trigger CI on `pull_request` for main + critical branches, NOT just `push: main`.
- For data jobs, use `paths:` filters so CI only runs when relevant files change.
- Set explicit `python-version:` — never rely on the default.
- Branch protection: every required check must be added in repo settings, not just defined in YAML.
- Secrets via `${{ secrets.NAME }}`. Never echo secrets to logs.
- Job names should describe outcomes ("pytest", "dbt-build-and-test"), not infrastructure ("ubuntu-job-1").
```

- [ ] No invented action names (`uses: dbt-labs/setup-dbt@v1` is real; `uses: dbt/dbt-runner@v1` may not be)

## Interview Prep — Common Questions for This Week's Material

> 5 questions a real interviewer would ask about CI/CD for data projects.

### IQ1. "Walk me through what happens when you open a PR on a project that has CI set up."

*What a good answer covers:*
- GitHub detects the PR event and consults `.github/workflows/*.yml`
- Each workflow with a matching trigger (`pull_request`) starts
- For each workflow, GitHub provisions one or more runners (clean VMs)
- Steps run in order: checkout, setup language runtime, install deps, run tests, run lints
- Each job's status (success/failure) is reported back as a "check" on the PR
- Branch protection rules block merge if required checks fail
- The author iterates: pushes more commits → workflow re-runs → checks update

*Likely follow-up:* "How would you debug a check that's failing only in CI but passes locally?" (Answer: reproduce in a clean container; check Python version, locale, timezone, missing env vars, hardcoded paths.)

### IQ2. "How do you keep CI fast as the project grows?"

*What a good answer covers:*
- **Cache aggressively**: pip, dbt artifacts (manifest, target/), node_modules — but key cache invalidation correctly so it doesn't lie
- **Parallelize**: split tests into multiple jobs by category (unit, integration, slow), run in parallel
- **Skip what didn't change**: `paths:` filters on triggers; Slim CI for dbt (only run changed models)
- **Move slow stuff off the PR path**: nightly schedule for full reconciliation, distribution profiling, load tests; PR runs the fast subset
- **Drop flaky tests**: a flaky test in CI is worse than no test — investigate and fix or quarantine

*Likely follow-up:* "What's the failure mode if CI takes 20 minutes?" (Answer: people stop waiting and merge. Or they bypass branch protection. Slow CI is unused CI.)

### IQ3. "How would you handle secrets in a CI/CD pipeline for dbt that needs warehouse credentials?"

*What a good answer covers:*
- Store secrets in GitHub Secrets (repo, environment, or org level depending on scope)
- Reference via `${{ secrets.NAME }}` — masked in logs automatically
- For multi-environment (dev/staging/prod), use GitHub Environments with environment-specific secrets and approval gates
- Never commit secrets, even encrypted, to the repo
- Rotate periodically; consider OIDC for cloud providers (no long-lived secrets — short-lived tokens issued per workflow run)
- For dbt specifically: write `profiles.yml` from secrets at runtime; never check in a `profiles.yml` with credentials

*Likely follow-up:* "What's OIDC, and why is it better than long-lived secrets?" (Answer: OpenID Connect — GitHub mints a short-lived token per workflow run, exchanged for cloud credentials via federated trust. No secret to leak; tokens expire in minutes.)

### IQ4. "What's the difference between running tests on every push to main vs. on every PR? When do you use each?"

*What a good answer covers:*
- **PR-only**: catches bugs *before* they reach main. Fast feedback to the author. Required checks block merge. The standard.
- **Push to main**: a "double-check" — main should already be clean since PRs were tested, but pushes can happen via merge or admin override. Often runs a wider battery (deeper integration tests, deploy preview).
- **Both**: typical configuration. PR for fast feedback; push to main for the full suite + deployment.
- **Schedule**: catches issues that aren't tied to code changes — upstream data drift, dependency updates, certificate expirations.

*Likely follow-up:* "Have you ever had a test that only fails on the schedule trigger, never on PR or push?" (Answer: yes — usually data freshness checks, or tests that depend on external services that change independently of the code. They live on schedule because they're noisy elsewhere.)

### IQ5. "Walk me through how you'd set up CI for a dbt project from scratch."

*What a good answer covers:*
- Workflow triggers: `pull_request` for fast feedback, `push: main` for the canonical run
- Steps: checkout → setup Python → pip install dbt + adapter → write profiles.yml from secrets → `dbt deps` → `dbt seed` (if seeded data) → `dbt build` → `dbt source freshness` (production only)
- Use `dbt build` not `dbt run + dbt test` — fails fast when an upstream model's tests fail
- For real warehouses: use a CI-isolated schema (`schema: ci_${{ github.run_id }}`) so PRs don't pollute production
- For scale: implement Slim CI — build only changed models and their downstream, deferring to production manifest
- For alerting: post failures to Slack via a webhook step, or rely on GitHub's PR check UI

*Likely follow-up:* "What's the cost trade-off of running every dbt model on every PR?" (Answer: with a real warehouse, this can cost real money in compute (warehouse credits per query). Slim CI cuts it dramatically. With dbt-duckdb in CI, cost is just runner minutes — usually fine.)

## Answers — Self-checks

> Don't scroll here until you've attempted the questions for that day.

### Day 1 answers

- **Q1.1** — `git fetch` downloads remote changes but doesn't apply them to your working branch. `git pull` is `fetch` followed by `merge` (or `rebase`, depending on config). Fetch is safer when you want to inspect before merging.
- **Q1.2** — No. The secret is in git history (the previous commit still exists). `git rm` only removes it from the *current* working tree. To purge from history, you'd use `git filter-repo` or `BFG Repo-Cleaner`, then force-push and (more importantly) **rotate the leaked credential**. History rewriting doesn't unleak a secret that's already on someone's screen.
- **Q1.3** — Code review and CI. PRs create a moment to discuss changes before they merge, and they're the natural trigger for running tests against the proposed change in isolation. Pushing straight to main skips both.
- **Q1.4** — The technical fix (`git reflog` to recover) is straightforward; the cultural fix is harder. Force-pushing to a shared branch is a process violation; the team should have branch protection on main that blocks it. Also: a culture where one person can silently nuke shared work suggests bigger workflow issues to address.

### Day 2 answers

- **Q2.1** — `actions/checkout@v5` clones your repo into the runner's filesystem. Without it, the runner starts empty — your code isn't there, so any step that references it (`pytest`, `cat README.md`, etc.) fails with file-not-found errors.
- **Q2.2** — In parallel. Jobs are parallel by default. Add `needs: {job_name}` to make one wait on another.
- **Q2.3** — When you want a manual trigger — re-run a deploy, smoke-test something on demand, kick off a full reconciliation outside the normal schedule. It adds a "Run workflow" button in the GitHub UI without conflating it with code-change triggers.
- **Q2.4** — `@latest` floats to whatever's published — including breaking changes shipped overnight. Your workflow can break without you changing anything. Pin to a major (`@v5`) at minimum; SHA-pin (`@a1b2c3...`) for security-critical setups.

### Day 3 answers

- **Q3.1** — (1) Hardcoded path that exists locally but not in the runner (`/Users/me/data.csv` etc.). (2) Working directory mismatch — pytest runs from the runner's `$GITHUB_WORKSPACE`, your local shell may run from a subfolder. (3) A file you forgot to commit (in `.gitignore`, exists locally, missing in CI). Less common but worth checking: env vars, locale, timezone.
- **Q3.2** — It caches pip's download cache directory, keyed on a hash of `requirements.txt` (and a few other files). Updating `requirements.txt` invalidates the cache; otherwise it's reused across runs.
- **Q3.3** — Branch protection rules. CI without enforcement is just a notification — anyone can merge anyway. Configure required status checks in repo settings.
- **Q3.4** — `--tb=short` prints a 1–3 line summary per failure. `--tb=long` (default) dumps the full traceback. In CI, where you scroll through HTML logs, short tracebacks are far easier to scan, and the rich detail is rarely worth the noise.

### Day 4 answers

- **Q4.1** — `dbt build` runs models and their tests in dependency order, stopping a downstream model from running if its upstream tests fail. `dbt run && dbt test` runs *all* models first, then *all* tests — by then a broken upstream has already corrupted everything downstream. `build` fails fast and localizes the bug.
- **Q4.2** — In `~/.dbt/profiles.yml`, written at runtime by the workflow from secrets. Don't commit it because (a) it usually contains credentials, and (b) different environments need different profiles — a committed file is the wrong abstraction.
- **Q4.3** — Many valid: (1) cost — every PR run incurs warehouse compute. (2) Risk — a buggy PR could corrupt production data unless you carefully isolate the schema. (3) Concurrency conflicts — multiple PRs running in parallel against the same schema. (4) Latency — production warehouses can be slower for ad-hoc work. The CI-dedicated schema pattern (`schema: ci_${{ github.run_id }}`) addresses some but not all of these.
- **Q4.4** — `manifest.json` from a previous successful build (typically the latest main build). Slim CI compares the current PR's manifest to this "deferred state" to identify what changed. Without it, dbt has no diff baseline.

### End-of-week answers

**A1.** A workflow contains one or more jobs; each job runs in its own runner; each job has steps that execute in order. Jobs run in parallel by default unless `needs:` introduces a dependency.

**A2.** Because the runner starts with an empty filesystem. `actions/checkout` clones your repo into it; without it, your code isn't there for subsequent steps to use.

**A3.** `push` runs after a commit lands on a branch. `pull_request` runs when a PR is opened, updated, or reopened — *before* code merges. PR-triggered CI is what blocks bad code from merging; push-triggered CI is the safety net on main.

**A4.**
```yaml
on:
  schedule:
    - cron: '0 7 * * *'
```

**A5.** It caches pip's download cache, keyed on a hash of your `requirements.txt` (or `pyproject.toml`, etc.). When that file changes, the cache key changes and pip downloads fresh.

**A6.** Without branch protection, CI is informational only — failing checks don't actually prevent merge. Anyone with write access can merge a red PR. Branch protection (in repo settings) marks specific checks as required and blocks merge until they pass.

**A7.** `dbt build` runs models and tests interleaved by dependency — a downstream model doesn't run if its upstream's tests failed. `dbt run + dbt test` runs all models first, then all tests, so by the time tests fail the downstream models have already been built on bad data.

**A8.** In GitHub repo Settings → Secrets and variables → Actions. Reference as `${{ secrets.NAME }}` in your workflow YAML. They're masked in logs automatically.

**A9.** (1) Environment differences — Python version, OS, locale, timezone, missing env vars. (2) File state — uncommitted local files; hardcoded absolute paths. (3) External dependencies — APIs the test calls, services not available in CI.

**A10.** Verify it actually runs. Pin checks: every action exists; every version is real; cron expression is correct; secrets are referenced (not embedded); no hardcoded paths. Generated YAML often *looks* right and is subtly broken in ways only visible at runtime.
